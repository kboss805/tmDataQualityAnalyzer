# v3.5.1: a deep dive after v3.5.0

Agreed with the user on 2026-11-26, after v3.5.0 was built: go through the whole codebase for obvious efficiencies, loose ends
and out-of-date text, then cut v3.5.1 for whatever v3.5.0 missed. Each phase reports its findings before it changes anything;
the user decides what to act on. **Not committed to a date.**

## How it ships

Three pull requests and the release, so that CI runs four times and not a dozen:

| PR | Holds | Why it is separate |
| --- | --- | --- |
| 1. Text, leftovers and test speed | the manuals, README and walkthroughs read against v3.5.0; the figures; stale comments and mutant notes; the installer loose ends; the release skill; the project's notes; **the test speed-ups that need no upgrade** (`mutate.ps1`'s `-Parts` runs and a run-only-affected-lists mode: done as `eng\mutants_affected.ps1`; the shared collection was tried and reverted, section 5) | no product behaviour changes, quick to review; and the speed-ups make every later PR's local runs faster |
| 2. Code | the layer-by-layer sweep, the efficiency items, whatever is decided on a batch stacking | changes behaviour or speed; one local run of the soak and the throughput guard; reverts as a unit |
| 3. Dependencies and test trust | xunit v3 4.x and Avalonia 12.2, then the `all` parallel mode measured on top, the flake fixes, the full kept-mutant re-run | an upgrade that breaks something is isolated from our own changes, and it replaces the test executable CI and `mutate.ps1` run, so it never rides with the release |
| 4. Release | version, notes, figures, package | as for v3.5.0; **nothing else rides with it** |

- Each change is its own commit with its own changelog entry, so a bundle loses nothing.
- Run `eng\ci_local.ps1` (it mirrors CI) before every push, so the CI run is a formality.
- **The installer is checked once, at the end** (package, Sandbox, the hand checks). CI never builds or tests it. A change that
  touches `deploy\tmDataQualityAnalyzer.wxs` gets a local test build of the MSI to catch build errors, and the Sandbox waits
  for the release.

## 4. Efficiency

The open list from the 2026-11-21 review, each measured before and after, the soak and the throughput guard as the oracles:

- the native CSV writer sorts every sample (each series is already ordered; the output must stay byte for byte);
- series are copied to managed arrays on the UI thread after a run;
- the chart builds its `SeriesIndex` inside its draw;
- the unlocked scan path, and a channel scanned twice when it is in two modes;
- the readout's binary search on an unsorted X (an imported CSV): a wrong value, not a slow one;
- the unbounded gap fill on a corrupt multi-day time jump.

## 5. Tests: speed and trust

What needs no upgrade is PR 1's; the upgrade and what follows from it are PR 3's.

**Measured 2026-11-26** (the app suite, Release core, 914 tests):

- The suite's wall time is one chain locally. 35 of its 58 test files share `NativeCoreCollection`, so xunit runs them one at a
  time: 726 tests, 51.8 s; the other 188 tests (23.9 s) already overlap with it. The collection exists because two tests
  (`OpenToChartTests` and `TemplateBatchTests`) briefly point `TMDQ_CORE_DLL` at a missing file.
- **Tried in PR 1 and reverted.** Moving those two tests to a collection of their own that runs alone and dropping the shared
  collection took the suite from 53 s to 38 s on the 28-core development machine, but on the 4-core hosted runner it was no
  faster (79 and 98 s against `main`'s 87 to 97 s) and failed both runs with a recording "being used by another process" during
  a test's cleanup (`ShortRecordings`, then `TemplateBatchTests`), which could not be reproduced here. The gain exists only
  where cores are idle. Try it again only after PR 3's flake hunt has found that failure, and measure the hosted run.
- `ManualFiguresTests` is 15 s of the 52 s, the largest class by far: see whether its checks can be split from its rendering.
  (PR 1, with the collection.)
- **xunit 4's new `all` parallel mode** (PR 3) may add a little, but Avalonia's headless tests share one UI thread, so expect
  less than the collection change gives. Measure it after the upgrade; do not assume it.

**The kept-mutant run** (708 mutants: 386 app, 231 native, 91 managed). A mutant spends its time building, not testing (three app
mutants took 35.5 s in all, about 10 s each, against 1 to 3 s of tests), so no test-runner feature speeds it up. What does:

- run the lists in several worktrees at once with `-Parts` and `-Part` (they exist; this machine has 28 cores): PR 1;
- a mode that runs only the lists whose mutated files a change touches, a full re-run for the release alone: PR 1.

**Trust (PR 3):** a flake hunt (loop the app suite and collect), including the run log's time-gated "NN% read" lines, which still
vary between renders of the manual's figures (seen in PR 2: three figures differed only in them), and the recording "in use"
at a test's cleanup that the shared-collection change brought out on the hosted runner (PR 1): 14 `ChartPlotStateTests` failed in one run and never again, and four
other tests have each failed once (`ManualFiguresTests` cleanup, `EveryExportReadsBackAsItsSeriesAndExportsAgainByteForByte`,
the CSV memory guard, `PackageLicenceTests`); the full kept-mutant list re-run for drift.
