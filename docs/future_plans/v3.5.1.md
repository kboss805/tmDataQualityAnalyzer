# v3.5.1: a deep dive after v3.5.0

Agreed with the user on 2026-11-26, after v3.5.0 was built: go through the whole codebase for obvious efficiencies, loose ends
and out-of-date text, then cut v3.5.1 for whatever v3.5.0 missed. Each phase reports its findings before it changes anything;
the user decides what to act on. **Not committed to a date.**

## How it ships

Three pull requests and the release, so that CI runs four times and not a dozen:

| PR | Holds | Why it is separate |
| --- | --- | --- |
| 1. Text and leftovers | the manuals, README and walkthroughs read against v3.5.0; the figures; stale comments and mutant notes; the installer loose ends; the release skill; the project's notes | no behaviour change, quick to review |
| 2. Code | the layer-by-layer sweep, the efficiency items, whatever is decided on a batch stacking | changes behaviour or speed; one local run of the soak and the throughput guard; reverts as a unit |
| 3. Tests and dependencies | the test-suite speed-up, flake fixes, the kept-mutant re-run, Avalonia 12.2, xunit v3 4.x | an upgrade that breaks something is isolated from our own changes |
| 4. Release | version, notes, figures, package | as for v3.5.0 |

- Each change is its own commit with its own changelog entry, so a bundle loses nothing.
- Run `eng\ci_local.ps1` (it mirrors CI) before every push, so the CI run is a formality.
- **The installer is checked once, at the end** (package, Sandbox, the hand checks). CI never builds or tests it. A change that
  touches `deploy\tmDataQualityAnalyzer.wxs` gets a local test build of the MSI to catch build errors, and the Sandbox waits
  for the release.

## 4. Efficiency

The open list from the 2026-11-21 review, each measured before and after, the soak and the throughput guard as the oracles:

- the native CSV writer sorts every sample (each series is already ordered; the output must stay byte for byte);
- series are copied to managed arrays on the UI thread after a run;
- the chart builds its `SeriesIndex` inside its draw;
- the unlocked scan path, and a channel scanned twice when it is in two modes;
- the readout's binary search on an unsorted X (an imported CSV): a wrong value, not a slow one;
- the unbounded gap fill on a corrupt multi-day time jump.

## 5. Tests: speed and trust

**Measured 2026-11-26** (the app suite, Release core, 914 tests):

- The suite's wall time is one chain. 35 of its 58 test files share `NativeCoreCollection`, so xunit runs them one test at a
  time: 726 tests, 51.8 s; the other 188 tests (23.9 s) already overlap with it. The collection exists because two tests
  (`OpenToChartTests` and `TemplateBatchTests`) briefly point `TMDQ_CORE_DLL` at a missing file.
- Removing the collection from all 31 files took the suite from **53 s to 35 s**, 0 failures in two runs, with those two tests
  free to race. So: let the two tests give the core a path some other way (an injectable path in `NativeCore`), or move them
  to a collection of their own with `DisableParallelization`, and drop the shared collection.
- `ManualFiguresTests` is 15 s of the 52 s, the largest class by far: see whether its checks can be split from its rendering.
- **xunit 4's new `all` parallel mode** may add a little, but Avalonia's headless tests share one UI thread, so expect less than
  the collection change gives. Measure it after the upgrade; do not assume it.

**The kept-mutant run** (708 mutants: 386 app, 231 native, 91 managed). A mutant spends its time building, not testing (three app
mutants took 35.5 s in all, about 10 s each, against 1 to 3 s of tests), so no test-runner feature speeds it up. What does:

- run the lists in several worktrees at once with `-Parts` and `-Part` (they exist; this machine has 28 cores);
- a mode that runs only the lists whose mutated files a change touches, a full re-run for the release alone.

**Trust:** a flake hunt (loop the app suite and collect): 14 `ChartPlotStateTests` failed in one run and never again, and four
other tests have each failed once (`ManualFiguresTests` cleanup, `EveryExportReadsBackAsItsSeriesAndExportsAgainByteForByte`,
the CSV memory guard, `PackageLicenceTests`); the full kept-mutant list re-run for drift.
