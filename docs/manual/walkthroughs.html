Before you process: the two setup dialogs

Every stream you process is configured through the gear button on its row in Configure Streams. Which dialog opens depends on the row's Mode. Getting these fields right is the difference between a meaningful plot and a confident-looking wrong one, so they are worth understanding before the walkthroughs that use them.

Configure Frame Sync Lock

{{FIG:walk-fs-03-framesync-setup.png|The frame sync setup dialog, configured for a PRN 15 stream - which is what a new stream starts on, so a PRN 15 recording needs no pattern file loaded. The folder and disk buttons load and save the top three fields as a TOML file.|Configure Frame Sync Lock dialog showing frame sync pattern, mask, bits per frame, data rate and averaging period}}
FieldWhat it isWhat a wrong value does
Frame Sync The synchronisation pattern in hex, up to 64 bits. No frames are found at all. The log says the pattern was not located and the stream plots as a flat zero.
Frame Sync Mask Which bits of the pattern must match. FFFFFFFF means all of them. Too permissive a mask matches noise, so lock % reads high on a stream that is not really locked.
Bits Per Frame The minor frame length in bits. The scanner looks for the next sync in the wrong place. You typically see syncs found but few or no frames extracted.
Data Rate (Mbps) The stream's bit rate. Very little — see the note below.
Average Period The window each lock % figure is computed over: 1 s, 100 ms or 10 ms. Nothing is wrong, but a longer window smooths over brief dropouts and a shorter one produces far more points.
Derandomize Undo RNRZ-L randomisation before searching for the pattern. On a randomised stream, leaving this off means the pattern is never found. Turning it on for a stream that is not randomised has the same effect.
Invert Data Invert every bit before decoding. As above: an inverted stream left un-inverted finds no syncs.
Lock % does not depend on an exact data rate. It is measured as a proportion of the frame-sized bit slots actually traversed, not as time × bitrate. A slightly wrong Data Rate will not skew the percentage. The field is there because the value is genuinely useful elsewhere, not because the metric is fragile.
Load and Save round-trip only three fields. The folder and disk buttons write Frame Sync, Frame Sync Mask and Bits Per Frame, and nothing else. Derandomize, Data Rate and Average Period are deliberately treated as per-session choices and are not saved, and neither is Legacy Chapter 10 — which is not in this dialog at all, because it describes the recording rather than the stream. This is intended, not an oversight: a pattern file describes a frame format, which is a property of the telemetry, while the others describe how you happen to be looking at it today. If you reload a file and those toggles are back at their defaults, nothing was lost.

Configure Receiver SNR

{{FIG:walk-snr-02-receiver-setup.png|The receiver setup dialog. The upper half is the same frame sync configuration as above; the lower half describes how receiver samples are laid out and converted.|Configure Receiver SNR dialog showing frame sync fields plus polarity, slope, scale, receiver count and channels per receiver}}

The top half is identical to the frame sync dialog and behaves the same way — an SNR stream still has to be frame-synchronised before anything can be read out of it. The lower half describes the receiver data:

FieldWhat it isWhat a wrong value does
Num Rcvrs and Num Channels How many receivers the frame carries, and how many channels each has (typically three: left, right, combined). Their product is the total channel count. Reading the wrong words out of the frame, so curves appear that are really other channels' data.
Polarity Whether the raw count rises or falls with signal strength. An upside-down plot: signal increases read as decreases.
Slope The receiver's output voltage range — 0–5 V, 0–10 V, ±5 V or ±10 V. Values scaled by a constant factor. The shape is right, the numbers are not.
Scale (dB/V) How many decibels one volt represents. As above — a linear error through every value.

The Apply Cal button, and the status text beside it, belong to non-linear step calibration. Until you attach a profile it reads (none — using linear calibration), meaning values are converted with the slope and scale above and nothing else. The calibration walkthrough below covers what that costs and how to improve it.

Apply to all at the bottom of either dialog copies these settings to every other selected stream of the same mode. On a file with sixteen identical receiver streams this turns sixteen configuration passes into one.

Walkthrough: frame sync lock

The goal: take a Chapter 10 recording, measure how well each PCM stream held frame synchronisation, and find the moments where it did not.

Step 1 — Open the recording

Use ≡ → Open… (or Ctrl+O), or drag a .ch10 file onto the window.

{{FIG:walk-fs-01-open.png|Opening a Chapter 10 recording. The file type filter shows only .ch10 files.|Open Chapter 10 File dialog with a .ch10 file selected}}

The application reads the file's TMATS metadata — not the data itself, which is why this is quick even on a multi-gigabyte recording — and opens the Configure Streams dialog listing every PCM channel it found.

Step 2 — Choose which streams to process, and how

{{FIG:walk-fs-02-configure-streams.png|Configure Streams. Three streams are selected for processing; the fourth is switched off and greys out. The Ready column shows at a glance which are fully configured.|Configure Streams dialog with four PCM channels, three enabled, showing green and red ready indicators}}

For each stream you want to measure, switch Process on and leave Mode at Frame Sync Lock. Then open its gear dialog and fill in the frame sync fields described in Before you process.

Watch the Ready column as you go. It is the dialog telling you whether it has enough information to run:

  • ✓ — configured and ready to process.
  • ✗ — selected for processing but not yet configured. Open the gear dialog.
  • ✗ — not selected. Nothing is required of it.

Two settings at the top of the dialog describe the recording rather than a stream, so they apply to every channel in the file:

  • Time Channel — every stream is timestamped from it, so all the curves share one time axis.
  • Legacy Chapter 10 — leave it off for ordinary recordings; turn it on for recordings from older equipment. Byte order belongs to the recorder that wrote the file, not to any one channel, which is why it sits here rather than behind a row's gear. If no stream in the file finds sync, try this before anything else.

Step 3 — Process

Press Process. The file is read once, with every selected stream decoded in parallel, so processing four streams costs little more than processing one.

{{FIG:walk-fs-04-processing.png|Processing under way. The log fills in beside the progress dialog, reporting each stream as it completes.|Processing progress dialog at 74 percent with the log showing per-stream progress}}

The log is worth reading rather than ignoring. Each stream reports the bytes it processed, the syncs it found and the frames it extracted — the quickest way to notice that a stream was misconfigured is a large sync count with almost no frames.

Step 4 — Read the plot

{{FIG:FrameSync Perctentage Plot with Legend.png|Lock % over time. These streams hold near 100% and drop vertically to zero at loss of lock — the cliffs are the events worth investigating.|Frame sync lock percentage plot with four streams near 100 percent dropping to zero}}

The left axis is the percentage of each averaging window in which the stream held lock. There is no right-hand axis here because this recording carries no receiver data — an axis appears only when something is plotted against it.

Healthy streams sit near 100%. What matters is the cliffs: vertical drops to zero where synchronisation was lost. Their width is how long the outage lasted and their position is when.

Step 5 — Switch to accumulation

Press V, or use the Show Accumulation button on the chart.

{{FIG:Frame Error Accumulation Plot with Legend.png|The same streams as accumulated missed frames. Each rise is frames lost at one of the cliffs above; a flat line means nothing was missed.|Accumulated missed frames plot showing step increases where lock was lost}}

Lock % answers "how good was the link at this moment"; accumulation answers "how much data did I actually lose". A stream that dips briefly but often can look worse than one long outage on the percentage plot while costing far fewer frames — the accumulation view settles which is which.

Step 6 — Export

Right-click the chart and choose Export…. You can produce an image, the underlying data as CSV, and the log text in one action; see Import & export for exactly what each contains.

Walkthrough: receiver SNR

The goal: take a recording containing receiver AGC samples and plot each receiver channel's signal strength in decibels over time.

This is the workflow to run first on any AGC recording. It uses the straightforward linear conversion, which is enough to see the shape of the data and to confirm you are reading the right words out of the frame. The calibration walkthrough that follows builds on it.

Step 1 — Set the stream's mode

Open the recording as before. In Configure Streams, switch Process on for the AGC stream and change its Mode to Receiver SNR.

{{FIG:walk-snr-01-mode-select.png|A stream switched to Receiver SNR. Mode decides which setup dialog the gear button opens, so change it before configuring the stream rather than after.|Configure Streams dialog with one row set to Receiver SNR mode and a green ready indicator}}
Mode decides which dialog the gear opens. Change it first: settings entered in the frame sync dialog do not carry over to the receiver dialog, so configuring a stream and then switching its mode means configuring it again.

Step 2 — Describe the receiver layout

Open the gear dialog and fill in the fields covered in Before you process. The frame sync half is exactly as it was for a frame sync stream — an AGC stream still has to be synchronised before anything can be read out of it. The receiver half tells the application how to find and convert the samples: how many receivers, how many channels each, the voltage range, and how many decibels a volt represents.

Rather than typing all of that for every recording from a given system, load a saved receiver parameters file. It carries the word map — which word in the frame belongs to which receiver and channel — along with the polarity, slope and scale.

{{FIG:walk-snr-03-load-params.png|Loading a receiver parameters file. These are per-installation rather than per-recording, so one file usually serves every recording from the same hardware.|File dialog for selecting a receiver parameters TOML file}}
A receiver parameters file describes the hardware, not the flight. One file typically covers every recording from the same installation, which is why these are worth keeping alongside your recordings.

Step 3 — Process

Press Process. The log reports the sample count and, importantly, the channel count for the stream — something like 184 samples, 48 channel(s). If the channel count is not what you expect, the receiver and channel numbers in the setup dialog do not match the recording, and everything downstream will be wrong.

Step 4 — Read the plot

{{FIG:Uncalibrated SNR Plot with Legend.png|Receiver SNR over time, converted linearly. This recording is a calibration sweep, so the trace climbs in deliberate steps; ordinary flight data is far less tidy. The legend lists every channel that was processed - all forty-eight of them.|Receiver SNR staircase plot with a legend listing forty-eight receiver channels}}

SNR is plotted against the right-hand axis, in decibels. There is no left-hand axis here because this recording carries no frame sync streams — an axis appears only when something is plotted against it, so which axes you see tells you what kind of data is loaded. In the figure above the legend covers the right-hand scale, which is the first sign that forty-eight channels is more than one plot can usefully carry.

The recording shown is a calibration sweep, which is why it climbs in neat steps. On real flight data you are looking for the shape instead: sustained levels, the depth and duration of fades, and whether channels that should track each other actually do.

Step 5 — Narrow it down

A fully populated receiver frame carries forty-eight channels, which is far more than can be read at once. Right-click the chart and choose Customize View… to show only what you care about.

{{FIG:walk-cust-02-snr-tree.png|The Receiver SNR tab groups channels by receiver, so a whole receiver can be shown or hidden in one click. Here one receiver is expanded with two of its three channels selected.|Customize Plot Series dialog showing the receiver tree with one group partially checked}}

Channels are grouped by receiver, and a group's checkbox reflects its children: ticked when all are shown, empty when none are, and filled when only some are. That third state is not an error — it is the tree telling you the receiver is partly selected. Clicking it selects or clears the whole group.

Hiding a channel changes the picture, not the data. An exported image contains only what is visible, but an exported CSV contains every channel that was processed, hidden or not. See Import & export.

Where to go next

If the steps in your data are uneven, or channels that were fed the same signal do not agree with one another, the linear conversion is the likely reason. The calibration walkthrough replaces it with a measured one.

Walkthrough: receiver SNR with step calibration

A receiver reports signal strength as a raw count. Turning that into decibels needs a conversion, and the application offers two.

Linear conversion — the default — applies the voltage range and dB/V scale from the setup dialog and nothing else. It assumes the receiver responds in a perfectly straight line across its whole range. Real receivers do not.

Non-linear step calibration measures the receiver instead of assuming it. You supply a recording of known signal levels, the application learns what raw count each level actually produced, and it interpolates between those measured points from then on.

What you need before you start

Two files, prepared in advance:

  • A calibration Chapter 10 recording — a capture of the receiver being fed a signal that steps through known levels, holding steady at each one.
  • A step TOML listing those levels, in the order they occur.
{{FIG:walk-cal-05-step-toml.png|A step configuration file. Each [[Step]] gives one level in dB, in the order the calibration recording steps through them. This one describes eleven steps from 0 to 60 dB in 6 dB increments.|A step configuration TOML open in a text editor showing eleven Step entries from 0 to 60 dB}}
The step file describes what was injected, not how long each level was held. Dwell time is not configured anywhere: each plateau is found by looking for a level that holds steady, so it does not matter whether a technician left each step for one second or ten.

Step 1 — Open the calibration dialog

Configure the receiver stream as usual, then press Apply Cal in the Receiver SNR setup dialog. Before any profile is attached, the text beside that button reads (none — using linear calibration), which is how you can tell at a glance what a stream is currently using.

{{FIG:walk-cal-01-extract-button.png|The Extract Calibration dialog as it opens, before either input file has been chosen.|Extract Calibration dialog with empty Step Cal File and Calibration Ch10 fields and clip values at zero}}

Step 2 — Choose the two files

Browse to the step TOML and the calibration recording. The dialog reports what it made of each as soon as you select it: how many steps it parsed, and how many channels it managed to calibrate.

{{FIG:walk-cal-03-clip-controls.png|Both files chosen and the clip controls set: 6 seconds trimmed from the start of the recording and 2 seconds from its end. The confirmations report eleven steps parsed and twelve of forty-eight channels calibrated.|Extract Calibration dialog populated with default.toml and step_cal, example.ch10, clip start 6 seconds and clip end 2 seconds, reporting 11 steps parsed and 12 of 48 channels calibrated}}

Step 3 — Trim the recording, if it needs it

Clip Start and Clip End discard that many seconds from each end of the calibration recording before anything is measured. They exist because real calibration recordings usually contain material that is not part of the sweep:

Both values are amounts to trim, not times. Clip Start is measured in from the beginning of the recording, and Clip End is measured back from its end — not from the beginning, and not from Clip Start. On a 65-second recording, Clip Start 6 and Clip End 2 keep the part from 6 s to 63 s. Entering Clip End 50 there does not mean "stop at 50 s": it trims the last 50 seconds and keeps only 6 s to 15 s, which leaves almost none of the sweep. If the two values add up to more than the whole recording, they are ignored and the entire recording is used — the dialog says so in amber beside the channel count, so a value that had no effect never looks like one that worked.
  • a turn-on transient at the beginning, while the signal generator settles at its first level;
  • an operator down-ramp at the end, where the level is walked back down after the sweep proper has finished.

Both look like plateaus to a detector that is asked only to find steady levels, and either can be mistaken for a real step. If the number of plateaus found does not match the number of steps in your file, trimming the ends is the first thing to try.

Trim only what is outside the sweep. The level the receiver holds before the generator starts stepping is usually the first step itself, and the top step runs right up to the moment the level drops back — so trimming too far at either end removes real steps rather than noise, and the channel count in the confirmation falls. Watch that count as you change the values: the dialog re-runs the extraction each time.

Step 4 — Read the result honestly

{{FIG:walk-cal-04-summary.png|The extraction summary for a recording whose sweep was injected into receivers 1, 3, 5 and 6. It names the receivers that calibrated, says why every other receiver fell back to linear, and flags receiver 1, which ran out of range before the sweep finished.|Calibration Extracted message box listing calibrated receivers 1, 3, 5 and 6, the receivers that fell back to linear with a reason for each, and receiver 1 holding at 48 dB}}

The summary is organised by receiver, because that is the unit you injected into. Read it top to bottom:

  • The count — how many channels received a measured profile, out of every channel in the word map.
  • Calibrated — the receivers whose channels all calibrated.
  • Check the step file / Check the word map — prompts that appear only when a result looks successful but may be wrong (see below).
  • Fell back to linear calibration — every other receiver, with the channels affected and the reason. A receiver that only partly calibrated is spelled out here rather than hidden in the count.
  • Calibrated only up to a saturated top — receivers that calibrated but ran out of range before the sweep finished (see below). This section, and one for receivers that needed a relaxed threshold, appear only when they apply.

The two "check" prompts. Both catch a setup mistake that otherwise calibrates without complaint:

  • Check the step file appears when a receiver stepped through more levels than the step file lists — for example eleven levels against an eight-step file. The extra levels at the start are set aside as lead-in, so every remaining step is paired with the wrong dB even though the receiver reports calibrated. One extra level is normal (a signal-generator turn-on transient) and does not trigger it.
  • Check the word map appears when one channel of a receiver swept and another never moved. That is what a receiver-parameters file that does not match the recording leaves behind: it files one receiver's words under another's name. A genuinely dead channel looks the same, so treat it as a prompt to check rather than a verdict.

Each fallback reason points at a different cause:

ReasonWhat it means
flat / no signal (held at n) The channel held one value for the whole recording, so the sweep is not in it. A value of 0 is usually a channel nothing was injected into; a value near 65535 is a receiver pinned at full scale. This is not a detection problem.
too few plateaus (x of n steps resolved) The channel moved, but through fewer distinct levels than your step file lists. Check that the step file matches the recording, then look for steps too close together to tell apart.
no monotonic sweep There were enough levels, but they did not climb (or fall) steadily — a noisy channel, or a response that reverses partway through.
no data Nothing was extracted for that channel at all.
A long fallback list is usually correct, not a failure. The recording in this figure carries forty-eight channels, and the sweep was injected into the left, right and combined channels of four receivers — twelve channels. Every other receiver reads flat / no signal because it saw no sweep, so there was nothing to measure. Refusing to build a profile out of noise is the right answer.

Channels that were not calibrated are neither broken nor excluded. They keep using the linear conversion from the setup dialog, exactly as before. A calibration run improves the channels it can measure and leaves the rest alone.

So the question to ask of this dialog is not "why so few?" but "did it calibrate the receivers I actually injected into?" If you swept four receivers and it names those four, it worked. If a receiver you swept is listed as falling back, the table at the end of this section is where to look.

A saturated receiver. Receiver 1 in the figure was driven past the top of its range: its 54 dB and 60 dB steps both read the same full-scale count, so they cannot be told apart. Rather than discard the whole channel, the application calibrates the steps that stayed in range and holds anything higher at the top one — 48 dB here. On the plot, that receiver climbs with the others and then flattens. The usual cause is a receiver gain set too high for the calibration levels; correcting it and re-recording recovers the full range.

Step 5 — Process, and compare against the uncalibrated run

Press OK, then Process. The profile is applied as the data is decoded.

{{FIG:Uncalibrated SNR Plot without Legend.png|Before: the same sweep converted linearly. The steps are uneven and the channels sit apart from one another, because a straight-line conversion cannot follow the receiver's real response.|Receiver SNR staircase without calibration showing uneven step heights and offset channels}} {{FIG:Calibrated SNR Plot without Legend.png|After: with a measured profile attached. The steps are evenly spaced and reach the levels that were injected, topping out at 60 dB, the last value in the step file.|Receiver SNR staircase with calibration applied showing evenly spaced steps reaching 60 dB}}

This comparison is the quickest way to confirm a calibration actually took. Look for two things: the steps should be evenly spaced, and the top step should sit at the highest level in your step file. If the staircase still looks uneven, the profile did not attach to the channels you are looking at.

Values beyond the calibrated range clamp to the nearest measured step rather than being extrapolated. A receiver driven past the range you calibrated reads the ceiling or floor value instead of diverging into a number no measurement supports.

When it does not work

What you seeLikely cause
A receiver you injected into reads flat / no signal, or fewer receivers calibrated than you swept The word map does not match the recording, so the sweep is being read from the wrong words. Check Num Rcvrs and Num Channels, and the receiver-parameters file if you loaded one — a map that skips a word per receiver moves every receiver after the first.
Calibration succeeded, but the steps land at the wrong levels The step file lists fewer steps than the recording holds. The extra levels at the start of the sweep are treated as lead-in and dropped, so every step is paired with the wrong dB. Make the step file describe every level that was injected.
A receiver's calibrated trace flattens below the top step The receiver saturated during the calibration sweep and its top steps could not be measured; readings above the last measured step hold there. Lower the receiver gain and re-record the calibration.
Plateaus found does not match the step count A turn-on transient or a trailing down-ramp is being counted as a step. Use Clip Start or Clip End to trim it.
The calibrated staircase runs the wrong way The receiver's raw count falls as signal rises. Set Polarity to match before extracting — the profile is built from raw counts, so polarity has to be right first.
It worked, then a later run was linear again Profiles last for the session only. See the note below.
Profiles are session-only and are never written to disk. Re-extract after restarting the application. A processing template stores the inputs — which step file and which calibration recording — rather than the measured profile, so a batch run started from a template uses the linear conversion. Non-linear calibration is a single-file workflow today.

Walkthrough: batch processing with a template

The goal: configure one recording, then apply that same configuration to as many others as you like without setting anything up again.

This is worth doing whenever you have a run of recordings from the same installation — the same receivers, the same PCM channels, the same frame formats. Configuring each one by hand is not just tedious; it is an opportunity to enter a slightly different value and not notice.

Step 1 — Get one file exactly right

Open a representative recording and configure it as in the walkthroughs above: modes, frame sync fields, receiver layout. Process it, and check the plot actually looks correct.

This is the step worth being fussy about. Everything that follows copies this file's configuration, so an error here is an error in every file you process afterwards.

If you intend to rename or recolour series, do it now as well — a template can carry those choices, so every recording in the batch comes out with the same colours for the same channels.

Step 2 — Save it as a template

Choose ≡ → Save as Template….

{{FIG:walk-batch-01-save-template.png|Saving a template. Give it a name that identifies the installation or aircraft rather than the recording it came from, since it will be applied to many others.|Save as Template file dialog writing a JSON template file}}

A template is a small .json file holding the per-stream configuration and, optionally, each series' name and colour. It contains no file paths, so it is not tied to the recording it was built from — it describes a setup, and can be kept alongside the receiver parameters files for the same installation.

Step 3 — Apply it to a set of recordings

Choose ≡ → Apply Template to Files…, pick the template, then select any number of .ch10 files. Before anything is processed, each file is checked against the template and the result is reported.

{{FIG:walk-batch-02-apply-dialog.png|The batch dialog reports its decision per file before running. Here three files match and one is rejected, with the channel differences that caused it spelled out.|Batch Process Files dialog listing three matching files with green ticks and one rejected file with a red cross and its reason}}

Read this list before pressing Process. Each file is marked:

  • ✓ — the file's PCM channel IDs match the template exactly, and it will be processed.
  • ✗ — they do not, and it will be skipped. The reason names the channels that are missing and the ones that are unexpectedly present.
The match has to be exact, and that is deliberate. A file with even one extra or missing channel is rejected rather than partly processed. The template addresses streams by channel ID, so applying it to a file whose channel set differs could silently attach one channel's settings to a different physical channel — producing a plot that looks entirely reasonable and is wrong. A skipped file you can see is better than a mislabelled result you cannot.

Two options are worth knowing before you run it:

  • Reuse the template's saved series names and colors — on by default. Every file comes out with the same channel in the same colour, which is what makes the results comparable at a glance.
  • Also export a CSV + plot images per file — writes, for each recording, a CSV plus two images named after the source file: …_framesync_lock.png and …_missed_frames.png. This is the option that turns a batch run into a folder of results you can hand to someone else.

Step 4 — Review the results

Every processed file stays loaded. Right-click the chart and use Plot File to choose which one you are looking at.

{{FIG:walk-batch-03-plot-file-menu.png|After a batch run, Plot File lists every recording that was processed. All files (overlaid) draws them together on one time axis.|Plot File submenu listing three processed recordings plus an All files overlaid option}}

Two ways to use this. Pick a single file to review each recording on its own, with the time axis zoomed to that recording's span. Or choose All files (overlaid) to draw every recording on one axis, which is how you spot the one that behaved differently from the rest.

Selecting a file here is a display filter, not a reload — nothing is re-processed, and your per-series visibility choices survive switching between files.

What a template does not carry

Non-linear calibration profiles are not stored in a template. A template records which step file and which calibration recording were used — the inputs — but not the measured profile itself, because profiles last only for the session in which they were extracted. A batch run therefore converts receiver values using the linear slope and scale. If you need measured calibration, process those recordings individually and extract it for each, as in the calibration walkthrough.
